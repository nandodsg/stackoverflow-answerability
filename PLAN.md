# Plan

Working plan for the Stack Overflow answerability take-home. Specs live in [`specs/`](specs/); this file tracks
scope, schedule and decisions.

## Goal

1. **Answer the three prompts exactly** — the gate. A reviewer who reads only the README must get correct, sourced
   answers with assumptions, confidence and limitations.
2. Build those answers the way an analytics team should run them: **spec → dbt models → tests → governed metrics**.
   Every extra must serve a prompt, not sit beside it.

## Scope (Tier 2)

| Piece | What | Serves |
|---|---|---|
| Specs | `specs/00N-*.md`: definitions, grain, assumptions, acceptance criteria — written before SQL | all prompts |
| dbt project | `dbt-bigquery`; public dataset as sources; staging → intermediate → marts in project `so-answerability`. A clone sets one env var for its own GCP project (tracked `profiles.example.yml`); the one-time `post_history` text-scan model is tagged and left out of default builds | all prompts |
| Testing strategy | `TESTING.md` + generic, unit, singular/reconciliation tests, a snapshot check in place of source freshness, model contracts; each acceptance criterion maps to a test | data quality grading criterion |
| Semantic layer | MetricFlow semantic models + metrics defined once; README numbers reproduced with `mf query` | metric consistency across prompts |
| Executable queries | `queries/q1.sql`, `q2.sql`, `q3.sql`: compiled, commented, run in the BigQuery console (no dbt needed). `q1` and `q2` are self-contained: every model is inlined down to `bigquery-public-data.stackoverflow`. `q3` also reads the two stored text-scan tables and the label seed by name (setup steps in its header). All three are generated by a script from the dbt models and never hand-edited | submission item 3 |
| Data architecture | A "This solution's data architecture" section and diagram: public dataset → sources → staging → intermediate (hub, one-time text scans) → marts → semantic layer → `queries/` and README numbers, with where tests, cost guardrails and the leakage checks sit. Written once, used in the README and in the presentation | reviewer orientation; the "how it is built" half of the answer |
| Presentation | One hand-built HTML page in the repo (`presentation/`), hosted at a public URL (GitHub Pages), that works both as slides for a 20–30 minute live walkthrough (one chapter per screen, arrow keys step through) and as a page a reader scrolls. Chapters: the three questions, the data and its traps, decisions made with evidence (D1–D4 with their EDA), the data architecture, one chapter per answer, quality and cost (acceptance criterion → test, the leakage warnings, byte caps and real spend), limitations, how it was built; every answer chapter carries a "how we know" strip (evidence, the tests that guard it, what it cost). It does not call BigQuery: a script exports the final marts to files in `presentation/data/` (CSV, with the CC BY-SA attribution), and DuckDB-WASM runs the SQL shown next to each headline number in the browser, so a number on the page is the result of the query beside it and can be changed live. Dark theme with one colour per prompt and animation (chapter transitions, highlights, drawn charts, an animated architecture diagram), with reduced-motion and no-JavaScript fallbacks | the live walkthrough; showing the engineering behind the answers |
| CI | GitHub Actions without warehouse access: `dbt parse`, `mf validate-configs --skip-dw` and the Python checks on every push, plus the job that deploys the presentation to GitHub Pages | keeps the project and the page buildable from a clean checkout |

Out of scope: Dagster, dbt MCP, a multi-page storytelling site (Evidence / Tableau Public; the presentation's in-browser SQL covers what it would add), CI that runs `dbt build` against BigQuery (it would need a cloud identity for the runner and would spend the query quota). Hosted `dbt docs` only if time remains.

  Tagged `dbt` among others: 3 / 96 / 224 / 351 (2019–2022). Exactly `python`: 5.7K–16.3K per year.

  `dbt build` if needed after late December 2026.
